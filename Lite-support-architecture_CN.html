Lite-support 技术架构与流程图

工单 + 知识库系统 · http://192.168.254.10:12345 · 2026-09-18（至第 27 轮）

1. 技术栈清单

一句话概括：后端 FastAPI + SQLite，前端零框架零打包的原生 ES Module SPA。

层技术 / 文件说明
前端框架无框架（原生 ES Module） 不用 React/Vue，也没有 webpack/vite。手写 h() hyperscript 生成 DOM，hash 路由（#/tickets/12）。
前端frontend/js/app.js 单文件视图层，约 160 KB。所有页面（工单台/知识库/后台）都在这里。
前端css/app.css · js/i18n.js 手写 CSS（含亮/暗主题）；i18n 支持中 / 英 / 繁三语。
Web 框架FastAPI 0.141.1 + Starlette 1.6 ASGI，路由与依赖注入；backend/app.py 是路由总入口。
数据校验Pydantic 2请求体校验与序列化。
应用服务器Uvicorn 0.53单进程，监听 12345。
业务模块rbac.py 角色 / 权限 / 用户组。权限由「角色」和「组」两路派生后取并集。
业务模块tickets.py 工单全生命周期、邮件模板、入站自动建号。
业务模块mailer.py 163 邮箱 IMAP 收信 / SMTP 发信，正文解码（第 24 轮修复点）。
业务模块md.py convert.py desens.py backup.py captcha.py Markdown 渲染、文档转换（PDF/Word/Excel）、脱敏、备份、滑块验证码。
数据库SQLite（WAL 模式） /opt/Lite-support/data/app.db，单文件，无独立数据库服务。
关键依赖qrcode + pillow · pypdf · fpdf2 · markdown · python-docx · openpyxl 第 25 轮才发现 qrcode 一直躺在 requirements 里却从没被 import。
运行systemd 服务 Lite-support 用户 Lite，装于 /opt/Lite-support，venv .venv（Python 3.13）。
外部163 邮箱（IMAP + SMTP） 客户发信即建工单；建单 / 回复 / 建号都走邮件回执。

2. 架构分层

自上而下：浏览器 → ASGI 服务 → 业务模块 → 数据与外部系统

3. 工单入站链路

客户发一封邮件，经过这六步落到一张工单上。第 2 步是第 24 轮修掉的中文乱码，第 5 步是第 27 轮修掉的"回复被新开单"。

邮件路径：唯一会经过「解码」的一段，也是中文乱码唯一起因；第 5 步决定这封信是"回答某张单"还是"开一张新单"

4. 共享到知识库 → 关闭工单

工单沉淀为知识库文章；若工单尚未关闭，会先弹确认框（明说"会一并关闭"）。

可见性四档：公开 / 已注册 / 内部 / 指定用户组

5. 代理商 ↔ 客户绑定

管理员把客户挂到代理商名下，代理商的可见范围由此收敛；开单时二选一。

"能开单"不等于"能编客户"：客户名由后端钉死

6. 修复记录

第 27 轮（2026-09-18）：同一人回复自己的工单，却被新开了一张

线程匹配只认了工单号，身份校验又只认客户名　已修复
hotmail 用户从网页开了 LITE-SUPPORT-202609003，随后用邮件回复系统发出的通知， 结果被新开成 LITE-SUPPORT-202609004。
取证第一步是看真实 Subject：收件箱里那封是 Re: Re:[#LITE-SUPPORT-202609003] 救救我 —— 工单号就在标题里，所以问题不在正则，而在匹配到之后的身份校验。
根因：校验只比 customer_id / customer_name，而 customer_name 只有"由邮件开的"工单才有（建单时代理商分支才写入）。网页开的工单该字段为空， 于是同一个人用自己的地址回复自己的工单被判成陌生人，一路掉到"新开一张"。
修法（两处，缺一仍有洞）：
① _owns_ticket() —— 身份改为「creator_email / creator_id / ticket_participants 命中任一， 或客户/代理商域名匹配，内部同事放行」；域名规则降为最后一条兜底，不再是唯一判据。
② _match_by_subject() —— 工单号找不到时按标题兜底：标题归一化（去工单号、去堆叠 Re:/Fwd:、去括号空白）后与同一 owner 的工单比对，取最新一张。 刻意加围栏：只认未关闭 + 只认近 45 天，否则「无法登录」这种通用标题会被吸到一年前的旧单； 别人家的同名标题不许认领。返回结果带 matched_by=code|subject，兜底的猜测不静默。
顺带：通知标题统一走 thread_subject() —— 邮件开的工单标题本身就是 [CODE] 原题， 旧写法会拼成 Re:[#CODE] [CODE] 原题 并且每轮回复再叠一层 Re:。
数据修复：重复单的消息移回原单、参与者与告警改指、空壳工单删除，状态回到「客户已答复」； 动手前留热备 app.db.prethreadfix-20260918-090445。

第 26 轮（2026-09-18）：新建工单只剩工具栏，没有正文输入框

markdown 编辑器从未挂载它的输入框　已修复
mdEditor(ta) 负责把「格式工具栏 + 正文框」打包成一块：它取了 ta、建了 wrapper、挂了工具栏和提示行， 却没有 append ta 本身。5 个调用点都只把 ta 传进去、默认它会被挂载（提交时照样读 ta.value）， 所以坏的不是某一个页面，而是所有用到这个编辑器的界面：新建工单描述、工单回复框、知识库文章编辑、欢迎页、回复模板。
判据：样式表里 .md-editor textarea{border-radius:0 0 6px 6px} 只圆下角（工具栏只圆上角、无下边框）—— 说明设计上输入框就该在工具栏正下方，漏掉的是代码而不是设计。
是回归吗：翻 GitHub 上 17 个版本的 app.js，这个编辑器只出现在最近两个提交里，且从第一版起就缺这一行； 再往前一版，描述字段是直接放在 label 里的裸 textarea —— 这就解释了"以前有输入框、现在没有"。
修法：wrap.append(bar, ta)，顺序固定为工具栏 → 输入框 → 提示行。
顺带：index.html 的资源版本号升到 ?v=20260918e —— 服务端不发 Cache-Control， 不换版本号时浏览器可能按启发式缓存继续用旧脚本。

第 25 轮（2026-09-18）：代理商角色错配 + 两步验证二维码

① 代理商被错标成「客户」　已修复
netfuns@hotmail.com 在用户列表里角色显示为「客户」。查库发现组是对的（Partner-hotmail）、角色是错的。
根因：两条建号路径各写各的 —— 入站邮件自动建号 tickets.find_or_create_user() 硬编码了「客户」角色，随后调用的 align_internal_role() 只处理本站自有域名，代理商域直接漏过；而网页注册那条路反而有正确的三分支。 这个账号正是客户发信触发的自动建号产物。
修法：新增 rbac.domain_role_name()（从已挂的组反推角色，而不是重新匹配域名 —— 组才是单一事实来源，也避免循环依赖） + align_domain_role()（写入，沿用"人工选的角色一律不碰"的保守契约）。两条建号路径都改调它。存量数据全量审计后定点修正 1 例。
② 两步验证的二维码扫不出来　已修复
注册页面挂的是 api.qrserver.com/v1/code-16x16.php —— 这个端点本身就是错的（正确是 /v1/create-qr-code/）， 而且需要公网，本站是内网部署，所以用户只看到一个破图。
关键发现：qrcode 8.2 + pillow 本来就在 requirements.txt 和 venv 里，代码却从未 import 过。
修法：auth.qr_svg() 在服务端生成内联 SVG（不外呼、密钥不进 URL / referrer），三处响应都带上，前端内联显示并保留明文密钥兜底。
