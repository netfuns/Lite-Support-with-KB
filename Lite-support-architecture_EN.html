2. Architecture layers

Top to bottom: browser → ASGI server → business modules → data and external systems

3. Inbound ticket pipeline

A customer sends one e-mail; six steps later it is a ticket. Step 2 is the mojibake fixed in round 24; step 5 is the "reply opened a new ticket" bug fixed in round 27.

The mail path is the only one that decodes bytes, and the only source of mojibake; step 5 decides whether a message answers a ticket or opens a new one

4. Share to the knowledge base → close the ticket

A ticket is distilled into a knowledge-base article; if the ticket is still open, a confirmation box says plainly that it will be closed as well.

Four visibility tiers: public / registered / internal / selected user groups

5. Partner ↔ customer binding

An admin puts a customer under a partner; that binding is what narrows the partner's visibility. When opening a ticket there are two options.

"Can open tickets" is not "can edit customers": the customer name is pinned server-side

Round 27 (2026-09-18): one person replied to their own ticket and got a new one instead

Thread matching only looked at the ticket code, and the identity check only looked at the customer name　fixed
A hotmail user opened LITE-SUPPORT-202609003 from the web, then replied to the notification the system had sent — and that reply was opened as LITE-SUPPORT-202609004.
Step one of the investigation was reading the real Subject: the message in the inbox was Re: Re:[#LITE-SUPPORT-202609003] 救救我 — the code was right there in the subject, so the bug was not in the regex but in the identity check that runs after a match.
Root cause: the check compared only customer_id / customer_name, and customer_name is only ever set on tickets that were opened by e-mail (only the partner branch of ticket creation writes it). A web-created ticket leaves that column empty, so the same person replying from their own address to their own ticket was judged a stranger and fell all the way through to "open a new one".
The fix (two places — either one alone still leaves a hole):
① _owns_ticket() — identity becomes "any of creator_email / creator_id / ticket_participants matches, or the customer/partner domain matches, or the sender is an internal colleague"; the domain rule is demoted to a last-resort fallback instead of the only test.
② _match_by_subject() — when the ticket code finds nothing, fall back to the subject: normalise it (strip the code, strip stacked Re:/Fwd:, strip bracket whitespace) and compare it against tickets owned by the same person, taking the newest. Deliberately fenced: only tickets that are not closed, and only within the last 45 days — otherwise a generic subject like "cannot sign in" would be sucked onto a year-old ticket; and a same-named subject belonging to someone else must not be claimed. The result carries matched_by=code|subject, so a fallback guess is never silent.
Along the way: notification subjects now go through thread_subject() — a mail-opened ticket's title is already [CODE] original subject, and the old construction produced Re:[#CODE] [CODE] original subject and stacked another Re: on every round trip.
Data repair: the duplicate ticket's messages were moved back onto the original, participants and alerts re-pointed, the empty shell deleted, status returned to "customer replied"; a hot copy app.db.prethreadfix-20260918-090445 was taken before touching anything.

Round 26 (2026-09-18): the new-ticket page had a toolbar but no body input

The markdown editor never mounted its own textarea　fixed
mdEditor(ta) is supposed to package "format toolbar + body box" into one block: it took ta, built the wrapper, attached the toolbar and the hint line — but never appended ta itself. All five call sites passed ta in and assumed it would be mounted (submission still read ta.value, so the data flow looked fine), which means what broke was not one page but every screen that uses this editor: the new-ticket description, the ticket reply box, knowledge-base article editing, the welcome page and reply templates.
The tell: the stylesheet has .md-editor textarea{border-radius:0 0 6px 6px} — only the bottom corners rounded (the toolbar rounds only its top corners and has no bottom border) — so by design the box belongs directly under the toolbar. What was missing was code, not design.
A regression? Walking 17 versions of app.js on GitHub, this editor only appears in the last two commits and has been missing that line since its first version; one version earlier the description field was a bare textarea inside the label — which explains "there used to be an input box and now there isn't".
The fix: wrap.append(bar, ta), with the order fixed as toolbar → input → hint.
Along the way: the asset version in index.html moved to ?v=20260918e — the server sends no Cache-Control, so without a version bump a browser may keep using the old bundle on heuristic freshness.

Round 25 (2026-09-18): partner role mismatch + two-factor QR code

① A partner was labelled "customer"　fixed
netfuns@hotmail.com showed up as "customer" in the user list. Querying the database showed the group was right (Partner-hotmail) and the role was wrong.
Root cause: the two account-creation paths each wrote their own thing — inbound-mail provisioning, tickets.find_or_create_user(), hard-coded the "customer" role, and the align_internal_role() it then called only handled the site's own domains, so partner domains slipped straight through; the web registration path, by contrast, had the correct three-way branch. This account was exactly the product of customer mail triggering auto-provisioning.
The fix: a new rbac.domain_role_name() (derives the role from the groups already attached rather than re-matching the domain — the group is the single source of truth, and it avoids a circular import) plus align_domain_role() to write it, keeping the conservative contract that a role a human chose is never touched. Both provisioning paths now call it. A full audit of existing data produced exactly 1 correction.
② The two-factor QR code would not scan　fixed
The registration page pointed at api.qrserver.com/v1/code-16x16.php — that endpoint is simply wrong (the correct one is /v1/create-qr-code/), and it requires the public internet while this site is an intranet deployment, so users saw a broken image.
The key finding: qrcode 8.2 + pillow were already in requirements.txt and in the venv — the code had just never imported them.
The fix: auth.qr_svg() renders an inline SVG server-side (no outbound call, and the secret never enters a URL or a referrer), all three responses carry it, and the front end inlines it while still showing the plaintext secret as a fallback.
